# Architecture

This page describes the contracts Qompack actually ships, with a citation for each. It is not a
design document: where `plans/00-ARCHITECTURE.md` or `Qompack.md` describes something the code does
not do, the code wins and the difference is stated here.

Sources are cited inline as file paths. `Qompack.md` is the design document (v1.5, 2026-09-06);
`plans/00-ARCHITECTURE.md` is the architecture plan; `plans/V5-report.md` is the most recent
verification record. ADRs are indexed in [docs/adr/README.md](adr/README.md).

## 1. Process model

Qompack is one binary, `cmd/qompack`, invoked in three roles.

**Hook processes.** `plugin/hooks/hooks.json` registers seven hooks, each of which runs the binary
as a short-lived subcommand:

| Hook | Subcommand | Timeout in the manifest |
|---|---|---|
| `SessionStart` | `qompack session-start` | 15 s |
| `PostToolUse` (matcher `*`) | `qompack observe tool` | 5 s |
| `UserPromptSubmit` | `qompack observe prompt` | 5 s |
| `Stop` | `qompack observe stop` | 5 s |
| `SubagentStop` | `qompack observe stop --subagent` | 10 s |
| `PreCompact` | `qompack checkpoint` | 20 s |
| `SessionEnd` | `qompack flush` | 20 s |

Every entry is exec form: `command` is exactly the bundled executable —
`${CLAUDE_PLUGIN_ROOT}/bin/qompack`, or `bin/qompack.exe` in a windows bundle — and `args` is the
subcommand, so the host spawns the binary directly on every platform and no shell ever parses the
string (C1.11: the former shell-form string was a PowerShell parse error on Windows machines without
Git Bash). The manifest is therefore rendered per target; the committed `plugin/` tree is the
linux/darwin rendering. All four bundle files are generated
from one typed value (`internal/pluginmanifest/manifest.go`: "Generating all four from one Go value
is what makes it impossible for them to drift apart"), and `devtool plugin-validate` diffs the
generated bytes against the committed tree in CI. That package's own comment records that the exact
key names are "partly undocumented host contract and are expected to change (G9.3)".

`internal/cli` is the dispatch layer and a composition root. Its package comment states the rule
that governs every hook process: "a hook subcommand exits 0 no matter what happens inside it" —
unreadable stdin, malformed JSON, an unresolvable project root, a read-only store or a panic in the
handler are all logged and swallowed, and the host still receives valid JSON on stdout. A sidecar
"must never be the reason a session gets worse".

**The MCP server.** `plugin/.mcp.json` registers one server, `qompack`, as the binary with the
single argument `mcp`. Per `internal/mcp`'s package comment, the transport "is stdio and only
stdio": newline-delimited JSON-RPC 2.0 over the reader and writer its caller hands `Serve`, with no
listener, no port and no socket.

**The daemon.** `internal/daemon` is "the resident per-project process … the thing that holds the
store, the sketches and the scheduler in memory so a hook does not have to". Its stated reason for
existing is a budget: a hook has a 15 ms p99 budget (B-A) and cannot open a store, load sketches and
reconstruct scheduler state on every tool call, so "the daemon pays those costs once and the hook
pays only a connect-write-ack".

**What runs where.** The hook process parses its event, connects, writes and waits for an ACK. The
daemon does the work: it is the single writer of the store, and — per `internal/mcp`'s package
comment — the MCP *handlers* execute in the daemon too, not in the `qompack mcp` process. The stdio
process "is a transcoder": it advertises this package's own `ToolDefs`, so `tools/list` is
byte-identical on both sides, and forwards every `tools/call` over the local transport. That is not
only a performance choice: Claude Code launches an MCP server once per client and hands it no
`session_id`, so the daemon is also the only party that can resolve which session a call belongs to.

**IPC.** `internal/ipc` implements the transport: endpoint resolution, NDJSON request/response
framing, a one-byte ACK/NAK handshake, and "the spool that every failure path falls back to". It is
the only package permitted to import `net`, and its package comment is emphatic that this is not
network access: on Windows a named pipe ACL'd to the current user's SID, on POSIX a `SOCK_STREAM`
Unix domain socket, mode 0600 in a 0700 directory. Decision D10 — no network I/O, ever — is enforced
mechanically by CI's `security` job, which greps the import graph for `net/http`, `net/url` and
`crypto/tls` outside `internal/ipc`.

## 2. Write set and retention

Everything Qompack writes for a project lives under `<project>/.qompack/`.
`internal/paths/layout.go` names the directories, and `EnsureLayout` creates them at 0o700:

`objects/`, `index/`, `sketches/`, `dag/`, `grammar/`, `checkpoints/`, `pins/`, `eval/` (with
`replay/` and `opt/`), `records/`, `state/`, `run/`, `spool/`, `logs/`, `metrics/`, `tmp/`,
`migrate/` and `backup/`. `EnsureLayout` also writes `<project>/.qompack/.gitignore` containing
exactly `*\n`, so the store self-ignores even in a project whose own `.gitignore` is never touched.

Named files referenced elsewhere on this page: `checkpoints/NNNN.json` and
`checkpoints/MANIFEST.jsonl`, `index/observations.jsonl`, `records/eliminations.jsonl`,
`state/frontier.json`, `state/config-violations.json`, `sketches/tried.bloom`.

`internal/paths`'s package comment makes the §7.4 append-only invariant mechanical: "every function
in this package that can write into `.qompack` refuses to truncate or rewrite `checkpoints/`,
`pins/`, or `sketches/tried.bloom`" (`appendonly.go`: `IsProtected`, `OpenFile`, `AppendOnly`,
`AppendJSONL`, `CreateNew`, `ReplaceBloom`).

The write set is asserted, not asserted-about: `plans/V5-report.md` §27 records
`TestV5_NoPackageWritesOutsideDotQompack` running under the real binary, plus
`test/guards/writeset_test.go` and an extended append-only guard. §27 also records that retention
roots and GC are covered by the I-06.x rows and the phase-7 compaction tests, and that the
compaction tests rewrite by design and are documented as doing so.

**What is never written.** Secrets. `internal/redact` is the choke point: "secrets must never reach
`objects/`, so redaction is applied once, at `store.Put`/`PutBytes`, before canonicalization and
chunking — never as an after-the-fact audit step". Ten built-in rules run in a fixed order plus
whatever `runtime.redact.patterns` admits; redaction is idempotent and bounded in growth, and both
properties are fuzzed. A rule is deliberately allowed to match an entire input, because a tool
result that *is* nothing but a private key must still be fully redacted.

No telemetry is written or sent: `runtime.telemetry.enabled` is hardwired off and the key exists
only to say so (`docs/config-reference.md`).

## 3. Identity

`plans/00-ARCHITECTURE.md` §0.2 defines four closed enumerations. They are confirmed against
`internal/core/evidence.go`, which declares exactly these values:

- `core.Fidelity` ∈ {`exact`, `prefix`, `partial`, `redacted`, `truncated`, `binary`, `failure`,
  `unknown`}
- `core.Coverage` ∈ {`qompack_included`, `archive_only`, `native_load_observed`, `expired_deleted`,
  `unknown`}
- `core.EvidenceOutcome` ∈ {`ok`, `absent`, `unavailable`, `denied`, `corrupt`, `expired`,
  `uncertain`}
- `core.Authority` ∈ {`user_correction`, `explicit_decision`, `tool_observation`,
  `candidate_extraction`, `hypothesis`, `conflict`}

The architecture's rule for them: "Enumerations are closed and versioned; consumers receive them
through composition roots, never by importing a sibling layer."

Two identities are kept apart. `core.ObservationID` is Qompack-assigned per accepted host delivery
and "never derived from content"; content identity is the hash root of the canonicalised content.
Two deliveries with equal bytes are therefore two observations with one content identity. A host
`tool_use_id` is carried verbatim as `HostID` when supplied and is absent otherwise — never
synthesised. Ordering is recorded as `ArrivalSeq` beside the observed `Turn`, and observed order and
arrival order are never inferred from one another. A record without an envelope (`v`, `transform`,
`hash`) has fidelity `unknown`, not `exact`.

`internal/state` carries the authority rules as types: "Only `AuthorityUserCorrection` and
`AuthorityExplicitDecision` are authoritative; only they may supersede an authoritative record,
correct anything, or resolve a conflict. A hypothesis or a candidate extraction never becomes an
instruction by being newer." Records are append-only, a conflict is rendered *as* a conflict until
an authorized source resolves it, and scope fails closed.

## 4. Publication and durability

Publication is ordered (`plans/00-ARCHITECTURE.md` §0.2.2): durable object (fsynced) → verified
references (index lines naming the object, appended only after the object is durable and re-verified
by hash on read) → committed frontier / checkpoint visibility. A reference or frontier failure leaves
the object as a GC root; a capture failure leaves the host result in place and forbids any handle or
pointer that claims it recoverable.

Acknowledgement is idempotent by the persisted `ObservationID`: lease → handle → ack, so an
interrupted drain re-delivers the same observation instead of consuming it or minting a second
identity.

[ADR 0014](adr/0014-delivery-group-commit-and-ab-seal.md) records the delivery path's group commit
and the format-2 A/B seal as they are implemented and merged — it documents decisions already taken
rather than proposing new ones, and settles four of the twelve questions SP20-D1's design put to the
owner.

**Delivery journal segments.** The lease and acknowledgement journals are segmented (SP20-D4,
enabled by default since the V6 close-out). A segment's two journal files keep their fixed bounds —
65,536 entries and 64 MiB each — and reaching either rotates the journal rather than refusing: the
rotation archives the outgoing window (every lease, acknowledgement and terminal disposition) into
the generation store, an immutable Merkle radix over nonce, arrival, acknowledgement, terminal and
per-session frontier keys, stored as one pack file and one root pointer per generation, merging the
window's keys in the radix's own key order so each page is read and written about once; then it
stages the next segment, with a carried-lease file naming every archived lease that has no
acknowledgement, and commits the switch as one fsynced record in the segment authority's chained
log. Leases and acknowledgements wait while a window is archived: about 2 to 7 s for a full window
in the V6 close-out's measurements on loaded Windows and Linux hosts. The hot path never writes the
generation store: the active segment's journals are the record of the active window, and only a
settlement of an already-archived lease is mirrored at once. A new delivery is checked against the
active window first and the archive second, so a redelivery of any archived nonce returns its
original identity and a dormant session continues its arrivals densely. The original four files stay
in place as segment 0; its two seals are frozen when the first rotation has archived the window and
before its transition commits, so a build that predates segments refuses the journal instead of
re-minting arrivals. The daemon's memory and every lookup are bounded by the active window; disk
grows with history. Store GC reads the active segment's journals and its carried leases, never the
archived segments' journals, so a GC pass is bounded by the active window and the carried leases (a
carry beyond 65,536 leases halts the pass, which then collects nothing). Backup, the offline
delivery-seal check and `fsck --seal-check` read every segment.

Checkpoint durability is `internal/checkpoint`: the L4 checkpointer owns the immutable,
importance-ordered checkpoint artifact, the incrementally advancing draft that encodes closed
segments exactly once (the §4.6 DPI guard), the tiered truncation order, ground-truth pointer
validation, and decision extraction. The on-disk JSON shape is versioned (`SchemaVersion`) and
pinned against a frozen fixture. [ADR 0011](adr/0011-rehydration-budget-and-item-order.md) covers
the read end.

There is exactly one draft owner per session — the checkpointer's `FileWriter`, which owns `Begin`,
`Finalize` and `Abort` and adjudicates the DPI guard in one place.

**Open on this tree.** `plans/V5-report.md` §29 item 2 records two known regressions in enabled
scope that are not host questions: SP20-D1 (hot-path budget B-B red on the shipped leased delivery
path) and SP20-D2 (verify-on-read over the `GetChunk` and `Search` budgets). Both are carried to
V6-VERIFY under a recorded waiver, and the report states plainly that plan §8's gate of "no
unresolved mandatory regression" is therefore **not met**.

## 5. State authority and uncertainty

`internal/state` separates what Qompack *observed* from what it *believes*: "An observation is
immutable and lives elsewhere; a Record here is a statement DERIVED from one or more observations
and is identified only by their `core.ObservationID`s." Nothing in that package holds observation
bytes, rewrites an observation, or lets a record change its own authority after admission. Current
authority and historical reads are therefore distinct: a superseded, corrected or conflicted record
stays readable with links in both directions and a retained `Lineage.History`.

**The recorded partial.** `plans/V5-report.md` §24 records the uncertainty gate as **partial**: it
does not survive the digest surface under a blind ledger. Concretely (§29 item 11): the blind-ledger
digest renders a stale record as `[active]`, and pin records are stamped `mcp` because `IngestPin`
has no production caller. Both are routed and unruled, and the gate stays `partial` until they are
ruled. Read an uncertainty marking in a digest as a claim that has not been verified end to end.

## 6. Retrieval

The MCP tools are documented in [docs/mcp-tools.md](mcp-tools.md), generated from
`internal/mcp.ToolDefs`. Four contracts are worth stating here because they are easy to misread.

**`unavailable` is not `absent`.** [ADR 0013](adr/0013-migration-contracts.md) names "errors read as
absence" as a defect to be fixed and sets the rule: `absent` "may be asserted only with complete,
fresh coverage; anything less is `uncertain` or `unavailable` with a reason and a recovery
direction". `docs/mcp-tools.md` carries the same contract for `already_tried`: a failed ledger query
returns `unavailable`, and "unavailable or unrecognized states never establish absence or prohibit
an approach". An unavailable answer is never substituted with current content.

**`dropped` reports qualified coverage.** It retrieves Qompack's own recorded omissions for the
session — what Qompack did not carry, qualified by the coverage and fidelity of what it did carry.
`docs/mcp-tools.md` states the boundary in its own words: "This report does not establish what
remains in native context."

**An `ephemeral` tag does not mean native eviction.** Every retrieval response exposes
`_meta.qompack.ephemeral`. `docs/mcp-tools.md` states it directly: "this is not a host eviction
control or proof of native context retention". `internal/mcp`'s package comment says the same:
"Retrieval metadata marks Qompack representations ephemeral; it does not control host eviction or
establish native context retention."

**Spans are minimal by default.** A tool returning file content returns the smallest chunk-aligned
span covering the request, widened to a symbol boundary where one is known, with `full: true` as the
explicit escape hatch and a `next_span` for paging.

Capture, fidelity and coverage may be partial or unknown, and the response says which.

## 7. Checkpoint and rehydration

At `PreCompact` the checkpointer finalizes a checkpoint artifact; after the compaction, the
rehydrator builds the payload that `SessionStart source=compact` injects.

`qompack checkpoint` answers the host with the empty object and nothing else. The hooks reference
gives PreCompact no `hookSpecificOutput` variant and says the host discards its `systemMessage` and
`continue`, and Claude Code 2.1.280 rejected the focus instruction Qompack used to return there
(C1.12). The daemon still renders that instruction and records it, but it travels no further than
the IPC reply: every hook client passes the daemon's reply through `internal/hookio`'s
`ConformOutput`, which keeps only the fields the host accepts and acts on for the event being
answered — `additionalContext` and `systemMessage` for `SessionStart`, `UserPromptSubmit` and
`PostToolUse`, `systemMessage` for `Stop`/`SubagentStop`, nothing for `PreCompact` and `SessionEnd`,
and never `continue`. The table is pinned against a transcription of the documented schema in
`testdata/host/hooks-output-schema.json`.

That transcription also records the host's per-field cap: an `additionalContext` or `systemMessage`
over 10,000 characters is accepted, but Claude receives only a file path and a 2,000-character
preview in its place, and is not asked to read the file. The host counts UTF-16 code units — its
own code tests `field.length <= 1e4` (2.1.280; `hookio.HostChars`,
`plans/sdd/V6-closeout/rehydrate-cap/evidence/host-cap-unit.txt`). The hook client passes an
over-cap field through unchanged and logs a Loud line with its size (`hookio.HostCapOverruns`); for
the rehydration that path is now a defence that does not fire, because the payload is built to fit
([docs/cannot-do.md](cannot-do.md#the-host-delivers-at-most-10000-characters-of-injected-context-whole)).

Two things about that payload are load-bearing, per `internal/rehydrate`'s package comment. Its
**order** is normative — `ItemKind`'s constants are the importance order, and a rehydration that
reorders them is wrong even if it fits the budget, because position decides what survives
truncation. Its **size** is deliberately small.

**The host ceiling (owner decision D5, 2026-09-22).** The whole compact `additionalContext` — the
injection-tagged payload, its headings and separators, every handle, the overflow report, and the
contract probe the daemon appends — is at most 9,500 host characters
(`rehydrate.HostContextCeilingChars`), 500 under the host's 10,000. `rehydrate.Build` prices every
unit in tokens and in host characters and admits it only when it fits both; the character count is
exact, so the ceiling is a guarantee rather than an estimate. It is a host constant, not a
configuration key: nothing raises it, and the token budget below can only bound the payload lower.
Selection keeps the §8.6 order with whole records — tier 1 (the retrieval line first, then pinned
invariants and the verbatim original intent), then items 2–6a by their shares — and a record that
does not fit is left out whole, never cut. Every record left out is named in section 7 with the call
that restores it (`why(dec_…)`, `re_read(path)`, `expand(tool_use_id=…)`, `already_tried` with the
elimination's own target and approach, `Read` on the rule, `CLAUDE.md` or `SKILL.md` file, or the
checkpoint file and field); eliminations past `eliminationsTopN` stay one counted line, answered by
the standing `already_tried` query, and the checkpointer's own drops keep its detail. Section 7 is a
bounded prefix plus a counted tail (`… and N more; call
dropped()`), and its smallest form is reserved before anything else is admitted, so the report on
what is missing always fits. The complete list is persisted for `dropped()` regardless
([ADR 0011 §21](adr/0011-rehydration-budget-and-item-order.md)).

**What "8–12K" is and is not.** It is a historical Qompack-added target for the material Qompack
injects, recorded in [ADR 0011](adr/0011-rehydration-budget-and-item-order.md) and in `Qompack.md`
§8.6. It is not the total restored native context, and nothing here claims the native input shrinks:
what the host restores on its own is the host's business, and Qompack neither measures nor controls
it. The shipped defaults are `runtime.rehydrate.minTokens` `8000` and `runtime.rehydrate.maxTokens`
`12000`, with `checkpoint.budgetTokens` `12000` for the checkpoint artifact itself
(`docs/config-reference.md`). Since D5 the host ceiling binds first: 9,500 characters is roughly
2,400 tokens of prose, so the token keys now matter only when set below that.

Injection has an independent kill switch: `runtime.migration.reinjection.sessionStartCompact`
(default `true`). Setting it false disables injection without touching recording. It names the one
injection adapter that has been tested; `plans/MIGRATION-EVIDENCE.md` records injection as
"documented; installed behavior unknown" and "no PostCompact prerequisite".

## 8. Scheduler, observer, negative knowledge

**Scheduler (L3).** [ADR 0012](adr/0012-scheduler-l3.md) records the composite trigger, BOCD
changepoint detection, cache regimes and p-selection as shipped by SP-12, together with the idle
work and frontier advancement. Its configuration surface is the `scheduler` block of
`docs/config-reference.md`.

**Observer (L0).** [ADR 0008](adr/0008-observer-l0.md) records the capture layer: content-address
every tool result, canonicalize per tool, near-dedup, addressable tombstones, redundancy and
supersession detection, verbatim prompt capture and subagent capture.

**Negative knowledge.** [ADR 0009](adr/0009-negative-knowledge-bloom-as-cache.md) settles the one
thing about this layer that is most often got wrong, and its title says it: the bloom is a cache.
The records are the source of truth and every membership answer is checked against them. There is no
"safe false positive" property here and none is claimed — an elimination is a *conditional* fact,
and a false `already_tried` is a real cost. `sketches/tried.bloom` is append-only-protected, and
`internal/negknow` is where it lives.

**Slices are scores.** [ADR 0007](adr/0007-dag-slices-are-scores-not-drop-decisions.md): the
dependence-DAG slice produces a relevance score per node, not a binary keep/drop.

## 10. What is not supported

Each item names where the limit is recorded. The full page is [docs/cannot-do.md](cannot-do.md).

- **No native cuts, markers or history eviction.** `plans/MIGRATION-EVIDENCE.md`, "Capability
  decisions": history rewriting / native eviction is `unsupported` and `Excluded`; ephemeral
  metadata is a future representation hint only. `internal/mcp`'s package comment says the same of
  the `ephemeral` tag.
- **No model-compliance or native-byte proof.** `plans/MIGRATION-EVIDENCE.md` records injection as
  "documented; installed behavior unknown" and packaging as "repository-level met, installed-host
  unverified" (B01). Nothing here observes what the model did with an injected payload, or what
  bytes the host holds.
- **No reconstruction of a missing original.** `plans/00-ARCHITECTURE.md` §0.2.2: a capture failure
  "leaves the host result in place and forbids any handle or pointer that claims it recoverable". A
  record without an envelope is `unknown` fidelity, not `exact`.
- **No universal improvement claim.** `plans/V5-report.md` §26: no held-out task runs, stochastic
  baselines or quality trials were executed; SP-21's quality row is "inconclusive by construction"
  and recorded as such (§24).
- **No performance guarantee.** The budgets in `docs/config-reference.md` are budgets that CI
  gates, not promises about your machine. [ADR 0010](adr/0010-wall-clock-under-coload.md) exists
  because a wall-clock figure measured under co-load is not a judgement, and `plans/V5-report.md`
  §29 carries open reference-platform rows.
- **No name-availability guarantee.** Slash-command and MCP tool names are advertised by this
  plugin; whether a name is free in a given host session depends on what else that host has loaded.
  `plans/V5-report.md` §29 item 6 records the competing-hook matrix (T21-HOST-01) as needing an
  installed host and not yet run.
- **Subscription usage is not API price.** `plans/V5-report.md` §25 records estimated price as
  `unknown` with no rate table applied, and notes that a subscription allowance is not cash per
  token. Qompack's own ledger never writes an estimate as an invoice and never fills an unknown
  count with zero.

## Known divergence from the plan documents

`plans/00-ARCHITECTURE.md` is a planning document that later waves amend; `plans/V5-report.md` §24
carries an explicit plan-vs-code drift list (SP-10's gate table, SP-11's gates, SP-13's manifest and
installed transcript, SP-10's host-boundary correction) as `implemented_unverified` or `documented`,
routed to V6 planning. Where this page and a plan document disagree, this page follows the code and
says which code. Where neither can settle a question, it is marked unknown above rather than
guessed.
