# Qompack 0.3.1

Qompack 0.3.1 is a patch release on 0.3.0. It is built with Go 1.26.9 for eight standard-library
security advisories, fixes three of 0.3.0's known issues and one diagnostic counter, and changes
nothing else you can see. Qompack is a local sidecar plugin for Claude Code: it records what a
session's hooks deliver into a store under the project's `.qompack/` directory, seals a checkpoint
when the host is about to compact, puts a bounded rehydration block into the session after the
host's compaction, and answers recall, expansion and negative-knowledge questions through an MCP
server and six slash commands. It runs on your machine only and performs no network I/O.

[0.3.0's notes](https://github.com/AidanHT/qompack/blob/v0.3.0/docs/release-notes/v0.3.0.md#what-030-is-not)
say what Qompack is not, and all of it holds for 0.3.1: it does not compact anything, it is not
cache-aware in any way that reaches the host, it makes no claim that it improves recovery after a
compaction, task success or constraint retention, and it makes no performance or storage promise on
your machine. Its binaries are not code-signed.

The release decision is the V6 close-out's D81, with D82 and the rows that follow them
(`plans/V6-CLOSEOUT-CHECKLIST.md`). The changes since 0.3.0 are listed in
[CHANGELOG.md](https://github.com/AidanHT/qompack/blob/v0.3.1/CHANGELOG.md). Known issues are
numbered as in the close-out ledger (`plans/sdd/V6-closeout/w22-known-issues.md`).

## Security

0.3.1 is built with Go 1.26.9. 0.3.0 was built with Go 1.26.6, and eight advisories against that
toolchain's standard library were published after 0.3.0's release, all fixed in Go 1.26.9
(GO-2026-6603, -6604, -6607, -6608, -6611, -6612, -6613 and -6617). One concerns code Qompack
runs: GO-2026-6604. On Windows, when the last component of the path given to one of `os.Root`'s
`Mkdir`, `Rename`, `Remove`, `Chmod` and related methods is a junction, the call can act on the
junction's target outside the root. Qompack confines its store and state writes with `os.Root`, so
a junction planted inside a project's `.qompack/` directory could redirect one of them. Planting
one needs write access to that directory. The other seven are in `net/http`, `net/textproto` and
`crypto/tls` code that Qompack, which performs no network I/O, does not use. If you run 0.3.0 on
Windows, update (decision D83).

## What 0.3.1 fixes

- **No capture is dropped when Windows reuses a hook's process id (known issue 19).** A hook that
  cannot reach the daemon writes its capture to a fallback spool file under `.qompack/spool/`. In
  0.3.0 that file was named by the hook's process id alone, so on Windows a new hook that reused an
  earlier one's id appended to the same file. Once that file reached its 64 MiB cap while it waited
  to be consumed, a capture was dropped, and `LOUD.log` said so. Each hook now writes a file of its
  own, `client-<pid>-<16 hex>.ndjson`, whose name adds a random id. For the same reason, a prompt
  spooled by such a hook can no longer be replayed ahead of an earlier one (decision D38's
  residual). A `client-<pid>.ndjson` that a 0.3.0 hook left is still drained, in host order with the
  new files (D78(c), D81(c)(1)).
- **A checkpoint's drop report names every capture it leaves waiting (known issue 20).** When a
  compaction's checkpoint is sealed while some of the session's captures are still waiting in the
  daemon (queued for a busy worker, held only in its write-ahead log, or leased by an earlier
  daemon), the rehydration block's section 7 and `dropped()` now name them. A capture known only by
  its delivery lease is counted, and the summary says how many. The summary no longer says the disk
  was slow, which can be true only of a capture still in a hook's spool. Nothing was lost in 0.3.0
  or now: the daemon stores the captures right after, and `recall` and `expand` find them then
  (D73(b), D81(c)(4), D82).
- **`/qompack:status` no longer promises a last decision (known issue 17).** Its description now
  reads "Qompack status — mode, contracts, store, latency". The status page never showed a last
  decision. To see a recorded decision, run `/qompack:why <decision-id>` (D76(b), D81(c)(2)).
- **A diagnostic counter no longer counts a read that did not fail.**
  `checkpoint.decision_read_error` read 2 or 3 on healthy stores, because it counted a by-design read
  of an elimination's empty root. It now skips that read and still counts every other failure
  (D76(d), D81(c)(3)).

Everything else in 0.3.1 changes tests and CI, with no product change and no check loosened
(D81(c)(5)); the CHANGELOG lists it.

## Install and upgrade

Claude Code **2.1.224 or later** is required to install from the marketplace (archive sources). The
marketplace, `qompack`, has one entry per release target, each a zip on this release pinned by
sha256. **Install exactly one entry, the one for your machine**: every entry is the same plugin, and
two installed at once would register its hooks and MCP server twice.

| entry | install it on |
| --- | --- |
| `qompack-linux-amd64` | Linux, x86-64 |
| `qompack-linux-arm64` | Linux, ARM64 |
| `qompack-darwin-amd64` | macOS, Intel |
| `qompack-darwin-arm64` | macOS, Apple silicon |
| `qompack-windows-amd64` | Windows, x86-64 |
| `qompack-windows-arm64` | Windows, ARM64 |

```sh
# Add the marketplace from the repository. --sparse .claude-plugin checks out only the marketplace
# file: a full clone fails on Windows on the repository's long paths, and is slow everywhere.
claude plugin marketplace add --sparse .claude-plugin -- https://github.com/AidanHT/qompack.git
claude plugin install qompack-windows-amd64@qompack -s user
```

Replace `qompack-windows-amd64` with your machine's entry. The repository form reads
`.claude-plugin/marketplace.json` from the default branch. Adding this release's `marketplace.json`
asset by URL does not work: Claude Code treats every `github.com` URL as a git repository.

**Upgrading from 0.3.0.** Update the marketplace, then the entry you installed, and restart Claude
Code when the update says so:

```sh
claude plugin marketplace update qompack
claude plugin update qompack-windows-amd64@qompack -s user
```

`marketplace update` fetches the marketplace from the default branch, which offers 0.3.1 once this
release's marketplace pull request is merged
([docs/release.md §1](https://github.com/AidanHT/qompack/blob/v0.3.1/docs/release.md#1-procedure),
step 7). No data migration is needed: 0.3.1 keeps 0.3.0's store and state formats, and the only
on-disk name it changes is the fallback spool file's, whose 0.3.0 form the daemon still drains. The
plugin's manifest, hook and MCP server registrations and commands are 0.3.0's; only the version and
`/qompack:status`'s description differ. As for 0.3.0, the install from this release's marketplace
entries is rehearsed on Windows and Linux before the release is promoted (D53(h)(3), D81(c)(8)).
Updating, checking the checksums yourself and uninstalling are described in
[docs/install.md §9](https://github.com/AidanHT/qompack/blob/develop/docs/install.md#9-installing-from-the-public-marketplace).
Every zip is listed in this release's `checksums.txt`, and the host refuses an archive that does not
match its pin.

**Unsigned binaries.** The binaries carry no code signature. Gatekeeper, SmartScreen and Windows
Defender may refuse or flag them; Defender's machine-learning detection has flagged development
builds of this tree (decision D32). What to check and what to do is in
[docs/install.md §10](https://github.com/AidanHT/qompack/blob/v0.3.1/docs/install.md#10-unsigned-binaries-gatekeeper-smartscreen-and-defender)
and [troubleshooting §7](https://github.com/AidanHT/qompack/blob/v0.3.1/docs/troubleshooting.md#windows-defender-flags-qompackexe).

## Supported targets

0.3.1 ships the same six targets as 0.3.0, built from one source by one build path: linux/amd64,
linux/arm64, darwin/amd64, darwin/arm64, windows/amd64 and windows/arm64. It adds no evidence on
macOS or on either arm64 target. No Mac has installed Qompack into Claude Code, darwin/amd64 is
cross-compiled only, and linux/arm64 and windows/arm64 are cross-compiled and bundled, with no test
run on either architecture and no install. What 0.3.0's evidence shows on each target is in
[0.3.0's notes](https://github.com/AidanHT/qompack/blob/v0.3.0/docs/release-notes/v0.3.0.md#supported-targets-and-what-is-verified-where).

## Verified where

0.3.1's product code is 0.3.0's plus the fixes above, so 0.3.0's machine evidence does not carry to
it by a byte comparison. Its own evidence is the release gate of decision D81(c)(8), run on the
release commit: hosted `ci.yml` (ubuntu-latest, macos-latest and windows-latest) and `nightly.yml`;
the Linux `-race` run, as a non-root user, on the packages the fixes touch; the C1.16 rig under
decision D78's co-load (16 fsync writers and 4 CPU spinners), which must show 0 missing Reads and 0
`LOUD.log` spool drops; and `release-check --tag v0.3.1` on the reference host, windows/amd64, on AC
power. No live session or live evaluation is part of that gate; 0.3.0's live re-check and live
evaluation ran on 0.3.0's frozen bundle.
These figures are recorded in this paragraph once the gates have run, and the release is not published before they are.

## Known issues

0.3.0's known issues 1 to 16 and 18 are not fixed in 0.3.1 and carry over unchanged. They are
listed, in that order, under Known issues in
[0.3.0's release notes](https://github.com/AidanHT/qompack/blob/v0.3.0/docs/release-notes/v0.3.0.md#known-issues),
where 11 to 15 share one item; 0.3.1 fixes 17, 19 and 20. One of the carried issues concerns your
data:

- **18.** After a crash that left an object written but not indexed, the next session end's garbage
  collection deletes that object before it can be audited; no capture content is lost, `qompack
  fsck` still names the gap, and copying the store before the next session ends keeps the object
  ([backup](https://github.com/AidanHT/qompack/blob/v0.3.1/docs/backup.md); D76(c), D81(c)(6)).

0.3.0's
[known limits and accepted residuals](https://github.com/AidanHT/qompack/blob/v0.3.0/docs/release-notes/v0.3.0.md#known-limits-and-accepted-residuals)
hold for 0.3.1 too. One is narrower: a prompt captured out of host order no longer comes from a
0.3.1 hook's reused process id, only from the live-versus-spool race or from a spool file a 0.3.0
hook left (D35(b), D38).
