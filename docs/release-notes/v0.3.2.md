# Qompack 0.3.2

Qompack 0.3.2 is a release on 0.3.1. It changes what the rehydration block carries after a
compaction: small tool results are shown in full under their pointers, each tool pointer is the
call that fetches it, and the block reads as the session's own record. It also records an approach
you say did not work, shortens the text every session loads, and fixes known issue 21 and a Windows
daemon stop that could leave its pipe bound. Qompack is a
local sidecar plugin for Claude Code: it records what a session's hooks deliver into a store under
the project's `.qompack/` directory, seals a checkpoint when the host is about to compact, puts a
bounded rehydration block into the session after the host's compaction, and answers recall,
expansion and negative-knowledge questions through an MCP server and six slash commands. It runs on
your machine only and performs no network I/O.

The block changes answer what 0.3.0's live evaluation (C5.5) showed: in 20 sessions the model never
called a Qompack tool to follow a pointer, a 22-byte value restored only as a pointer was lost, and
in 3 sessions the model distrusted the block as injected content. No live evaluation is part of
0.3.2's release gate, and these notes do not claim that the changes improve recovery after a
compaction, task success or constraint retention.
[0.3.0's notes](https://github.com/AidanHT/qompack/blob/v0.3.0/docs/release-notes/v0.3.0.md#what-030-is-not)
say what Qompack is not, and all of it holds for 0.3.2: it does not compact anything, it is not
cache-aware in any way that reaches the host, and it makes no performance or storage promise on
your machine. Its binaries are not code-signed.

The fixes owed after 0.3.1 are decision D86, and the block's growth on the replay corpus is
accepted under decision D90. The changes since 0.3.1 are listed in
[CHANGELOG.md](https://github.com/AidanHT/qompack/blob/v0.3.2/CHANGELOG.md). Known issues are
numbered as in 0.3.0's and 0.3.1's notes.

## What changes for you

- **Small tool results come back in full.** After a compaction, a tool result of 512 bytes or less
  appears verbatim under its pointer in the block's section 6, up to 4 KiB of such results per
  block. It is the bytes `expand` would return for that result: read from the store only while the
  stored record still matches the checkpoint, shown only when its pointer's summary is shown and
  `expand` would serve it (a result with a path needs that path inside the project and allowed by
  your saved Read rules), and redacted with the current `runtime.redact` policy. A larger result, a
  binary one, or one that does not fit the block stays a pointer, as before. The rules are in
  [docs/security.md §1](https://github.com/AidanHT/qompack/blob/v0.3.2/docs/security.md#1-trust-boundaries).
- **Each tool pointer is a call you can copy.** A tool pointer now reads
  `expand(tool_use_id="toolu_…")`, the call that returns the stored result. A file pointer keeps
  its path, which is `re_read`'s whole argument, and the section's heading says that `expand` or
  `re_read` gives the full content.
- **The block reads as the session's own record.** Its heading is now "Qompack's record of this
  session before compaction" and its marker `<!-- qompack:session-record seq=N ver=V -->`; section
  2 says it holds the user's own words, verbatim. A block written by 0.3.1 or earlier, marked
  `qompack:injected`, is still recognized and stripped, so its text is not carried into the next
  checkpoint.
- **An approach you say did not work is recorded.** When a prompt of yours says so in one of a
  fixed list of phrases ("that didn't work", "we already tried", "that was a dead end", and a few
  more), the daemon records an elimination: its target is the last file edited in the turn you are
  answering, its approach the first line of Claude's reply in that turn, and its reason your
  prompt, the last two redacted with the current `runtime.redact` policy. `already_tried` and the
  block's section 3 can then name it. A statement after a turn that edited no file records nothing,
  and none of this runs while the hook waits.
- **Less fixed text in every session.** The MCP server's instructions and tool descriptions, which
  every session loads, are about a fifth smaller, and the slash-command descriptions are shorter.
  Tool names, arguments and behaviour are unchanged.

## What 0.3.2 fixes

- **A checkpoint no longer keeps a pointer to a removed file object without saying so (known issue
  21).** Finalize now checks each file pointer's stored content the way it checks a tool
  result's. A file whose stored copy is gone is left out of the checkpoint and named in its drop
  report (D86).
- **The daemon's warning when a `PreCompact` seals before every capture is replayed says how long
  the settle ran and why it stopped.** A host stall past the settle's bound, the designed degrade,
  can now be told from a defect (D84(b), D86).
- **On Windows, a daemon that stops frees its pipe.** The named-pipe library Qompack uses (go-winio
  v0.6.2) could lose the listener's Close when a connection attempt was pending, as one is after a
  hook checks that the daemon is alive. The stop then waited out its 2-second bound with the pipe
  name still bound until the process exited. The stop now repeats the Close until it takes effect,
  within the same bound.

Everything else in 0.3.2 changes tests, comments or repository files, with no product change; the
CHANGELOG lists it. A few of those change how a check reads, and the CHANGELOG says how for each:
the largest is the replay gate's re-recorded baseline (below), and rows that read the
maintainer-only records skip with a stated reason in a checkout without them, as on hosted CI.

## What the block's growth costs

The block is larger. On the replay gate's 24-session synthetic corpus, its tokens rise from 96,583
in 0.3.1 to 102,585, about 6%. Almost all of it is the `expand(tool_use_id="…")` label on each tool
pointer (5,850 tokens); the record framing adds 281 and section 6's new heading 77, and leaving out
the empty "blocked on: none" line saves 206. The replay has no store, so it shows no inlined
result: those come on top of that figure, at most 4 KiB per block, and the whole block stays within
its 9,500-character limit. The replay's estimate of the time to the first turn after a compaction
models latency from the same block tokens (800 ms plus 90 ms per 1,000 tokens), so it is the same
growth seen through that model: its median rises from 1,013 ms in 0.3.1 to 1,034 ms, 2.07%. This
trade is recorded under decision D90: the replay gate's committed baseline is re-recorded by the
replay driver with a sign-off for those two rows, and no cap or threshold moved. The sign-off
measures against the gate's previous baseline, which predates 0.3.1's own growth of 1.45%, so it
reads +7.75% for tokens (95,203 to 102,585) and +2.38% for the median (1,010 to 1,034 ms).

## Install and upgrade

Claude Code **2.1.224 or later** is required to install from the marketplace (archive sources). The
marketplace, `qompack`, has one entry per release target, each a zip on this release pinned by
sha256. **Install exactly one entry, the one for your machine**: every entry is the same plugin, and
two installed at once would register its hooks and MCP server twice.

| entry | install it on |
| --- | --- |
| `qompack-linux-amd64` | Linux, x86-64 |
| `qompack-linux-arm64` | Linux, ARM64 |
| `qompack-darwin-amd64` | macOS, Intel |
| `qompack-darwin-arm64` | macOS, Apple silicon |
| `qompack-windows-amd64` | Windows, x86-64 |
| `qompack-windows-arm64` | Windows, ARM64 |

```sh
# Add the marketplace from the repository. --sparse .claude-plugin checks out only the marketplace
# file: a full clone fails on Windows on the repository's long paths, and is slow everywhere.
claude plugin marketplace add --sparse .claude-plugin -- https://github.com/AidanHT/qompack.git
claude plugin install qompack-windows-amd64@qompack -s user
```

Replace `qompack-windows-amd64` with your machine's entry. The repository form reads
`.claude-plugin/marketplace.json` from the default branch. Adding this release's `marketplace.json`
asset by URL does not work: Claude Code treats every `github.com` URL as a git repository.

**Upgrading from 0.3.1 or 0.3.0.** Update the marketplace, then the entry you installed, and
restart Claude Code when the update says so:

```sh
claude plugin marketplace update qompack
claude plugin update qompack-windows-amd64@qompack -s user
```

`marketplace update` fetches the marketplace from the default branch, which offers 0.3.2 once this
release's marketplace pull request is merged
([docs/release.md §1](https://github.com/AidanHT/qompack/blob/v0.3.2/docs/release.md#1-procedure),
step 7). No data migration is needed: 0.3.2 keeps 0.3.1's store and state formats. Going back to
0.3.1 has one cost, listed under Known issues below. The plugin's manifest, hook and MCP server
registrations and commands are 0.3.1's; only the version and the slash-command descriptions
differ. As for earlier releases, the install from this release's marketplace entries is rehearsed
on Windows and Linux before the release is promoted (D53(h)(3)). Updating, checking the checksums
yourself and uninstalling are described in
[docs/install.md §9](https://github.com/AidanHT/qompack/blob/develop/docs/install.md#9-installing-from-the-public-marketplace).
Every zip is listed in this release's `checksums.txt`, and the host refuses an archive that does not
match its pin.

**Unsigned binaries.** The binaries carry no code signature. Gatekeeper, SmartScreen and Windows
Defender may refuse or flag them; Defender's machine-learning detection has flagged development
builds of this tree (decision D32). What to check and what to do is in
[docs/install.md §10](https://github.com/AidanHT/qompack/blob/v0.3.2/docs/install.md#10-unsigned-binaries-gatekeeper-smartscreen-and-defender)
and [troubleshooting §7](https://github.com/AidanHT/qompack/blob/v0.3.2/docs/troubleshooting.md#windows-defender-flags-qompackexe).

## Supported targets

0.3.2 ships the same six targets as 0.3.1, built from one source by one build path: linux/amd64,
linux/arm64, darwin/amd64, darwin/arm64, windows/amd64 and windows/arm64. It adds no evidence on
macOS or on either arm64 target. No Mac has installed Qompack into Claude Code, darwin/amd64 is
cross-compiled only, and linux/arm64 and windows/arm64 are cross-compiled and bundled, with no test
run on either architecture and no install. What 0.3.0's evidence shows on each target is in
[0.3.0's notes](https://github.com/AidanHT/qompack/blob/v0.3.0/docs/release-notes/v0.3.0.md#supported-targets-and-what-is-verified-where).

## Verified where

0.3.2's product code is 0.3.1's plus the changes above, so neither 0.3.1's machine evidence nor
0.3.0's carries to it by a byte comparison. Its own evidence is its release gate, run on the release
commit: hosted `ci.yml` (ubuntu-latest, macos-latest and windows-latest, with its `-race` legs and
the replay gate on the re-recorded baseline) and `nightly.yml`; and a night run on the reference
host, windows/amd64, on AC power: the C1.16 rig with no extra load and under decision D78's co-load
(16 fsync writers and 4 CPU spinners), each of which must show 0 missing Reads and 0 `LOUD.log`
spool drops, and `release-check --tag v0.3.2` in a scratch clone that holds the tag. No live
session or live evaluation is part of that gate; 0.3.0's live re-check and live evaluation ran on
0.3.0's frozen bundle.
On the release commit `9408430b`: hosted `ci.yml` run 38106193891 and `nightly.yml` run
38106495075 passed on their first attempts. On the reference host, on AC power, the C1.16 rig
accounted for every Read with 0 spool drops, with no extra load (2,515 Reads; compaction
`SessionStart` p99 94 ms) and under co-load (2,509 Reads, 653 of them in 757 client spool files;
p99 279 ms); `release-check --tag v0.3.2` passed all 18 of its steps; two bundle builds were
byte-identical across all 91 files; and the Windows timing set and X11, each run alone, passed.
Those two hot-path rows do not pass on every run on this host, with 0.3.1 as with 0.3.2: the timing
set failed `TestIntegration_HotPathWarmWithRealResidentState` the night before it passed (B-B p99
57.3 ms against 50). Run alone and alternated with 0.3.1 on one night, that row breached its 50 ms
p99 in 2 of 3 runs of 0.3.2 and in 2 of 4 of 0.3.1, with B-B p50 between 13 and 16 ms in every run
and the breach in the disk's fsync tail (B-B p99 115 to 131 ms), and one run of `test/e2e` failed
X11's arm without the ledger at B-A p99 53.2 ms. Where a run crossed the hot-path threshold the
hooks switched to spool submode, and every capture was delivered or deferred, none lost (decision
D94).

## Known issues

0.3.0's known issues 1 to 16 and 18 are not fixed in 0.3.2 and carry over unchanged. They are
listed, in that order, under Known issues in
[0.3.0's release notes](https://github.com/AidanHT/qompack/blob/v0.3.0/docs/release-notes/v0.3.0.md#known-issues),
where 11 to 15 share one item; 0.3.1 fixed 17, 19 and 20, and 0.3.2 fixes 21. One of the carried
issues concerns your data:

- **18.** After a crash that left an object written but not indexed, the next session end's garbage
  collection deletes that object before it can be audited; no capture content is lost, `qompack
  fsck` still names the gap, and copying the store before the next session ends keeps the object
  ([backup](https://github.com/AidanHT/qompack/blob/v0.3.2/docs/backup.md); D76(c), D81(c)(6)).

0.3.2 adds two:

- **Going back to 0.3.1 can carry one block forward.** A 0.3.1 or older binary does not recognize
  the new `qompack:session-record` marker, so after a downgrade one block written by 0.3.2 can be
  carried into the next checkpoint.
- **A stated elimination can be lost.** If the daemon stops between storing your prompt and
  recording the elimination it states, the elimination is not recorded. The prompt itself is
  stored, and `/qompack:pin --eliminated` or `record_eliminated` records the approach by hand.

0.3.0's
[known limits and accepted residuals](https://github.com/AidanHT/qompack/blob/v0.3.0/docs/release-notes/v0.3.0.md#known-limits-and-accepted-residuals)
hold for 0.3.2 as 0.3.1 narrowed them: a prompt captured out of host order comes only from the
live-versus-spool race or from a spool file a 0.3.0 hook left (D35(b), D38).
