# Qompack 0.3.0

Qompack is a local sidecar plugin for Claude Code. It records what a session's hooks deliver (tool
results, prompts and turn boundaries) into a store under the project's `.qompack/` directory, seals
a checkpoint when the host is about to compact, puts a bounded rehydration block of at most 9,500
characters into the session after the host's compaction, names what did not fit (in the block, or,
at a budget too small for even the shortest loss notice, in the drop report and `LOUD.log`), and
answers recall, expansion and negative-knowledge questions through an MCP server and six slash
commands.
It runs on your machine only and performs no network I/O. This is the first release published from
this repository; `v0.2.0` was an internal verification checkpoint.

The changes since `v0.2.0` are listed in
[CHANGELOG.md](https://github.com/AidanHT/qompack/blob/v0.3.0/CHANGELOG.md).

## What 0.3.0 is not

- **It does not compact anything.** Compaction is the host's. Qompack cannot request, veto, shape or
  time a compaction, and its `PreCompact` answer is the empty object.
- **It is not cache-aware in any way that reaches the host.** It cannot see, keep warm or change the
  host's prompt cache.
- **It makes no claim that it improves recovery after a compaction, task success or constraint
  retention.** The release's pre-registered live evaluation can show that Qompack does not make work
  after a compaction worse; a claim of improvement would need that outcome's 95 % lower bound above
  zero (`plans/sdd/V6-closeout/eval/preregistration.md`, amendment A8). These notes make no such
  claim.
- **It makes no performance or storage promise** on your machine, and its binaries are not
  code-signed.

## Install

Claude Code **2.1.224 or later** is required to install from the marketplace (archive sources);
0.3.0 was tested with Claude Code **2.1.280**. The marketplace, `qompack`, has one entry per release
target, each a zip on this release pinned by sha256. **Install exactly one entry, the one for your
machine**: every entry is the same plugin, and two installed at once would register its hooks and
MCP server twice.

| entry | install it on |
| --- | --- |
| `qompack-linux-amd64` | Linux, x86-64 |
| `qompack-linux-arm64` | Linux, ARM64 |
| `qompack-darwin-amd64` | macOS, Intel |
| `qompack-darwin-arm64` | macOS, Apple silicon |
| `qompack-windows-amd64` | Windows, x86-64 |
| `qompack-windows-arm64` | Windows, ARM64 |

```sh
# this release's own marketplace asset (pinned to 0.3.0; works for a pre-release too)
claude plugin marketplace add https://github.com/AidanHT/qompack/releases/download/v0.3.0/marketplace.json
claude plugin install qompack-windows-amd64@qompack -s user
```

Replace `qompack-windows-amd64` with your machine's entry. Adding the marketplace from the
repository or from the latest release's asset, which track later releases, and updating, checking
the checksums yourself and uninstalling are described in
[docs/install.md §9](https://github.com/AidanHT/qompack/blob/v0.3.0/docs/install.md#9-installing-from-the-public-marketplace).
Every zip is listed in this release's `checksums.txt`, and the host refuses an archive that does not
match its pin.

**Unsigned binaries.** The binaries carry no code signature. Gatekeeper, SmartScreen and Windows
Defender may refuse or flag them; Defender's machine-learning detection has flagged development
builds of this tree (decision D32). What to check and what to do is in
[docs/install.md §10](https://github.com/AidanHT/qompack/blob/v0.3.0/docs/install.md#10-unsigned-binaries-gatekeeper-smartscreen-and-defender)
and [troubleshooting §7](https://github.com/AidanHT/qompack/blob/v0.3.0/docs/troubleshooting.md#windows-defender-flags-qompackexe).

## Supported targets and what is verified where

All six targets are built from one source by one build path, reproducibly: two builds of release
candidate 6 were byte-identical across all 91 bundle files. This release is release candidate 8
(decision D58(e)), which changes product code over candidates 6 and 7, so their machine evidence
does not carry to it by a byte comparison. Candidate 8's own evidence supplies it: its night chain
on the frozen tree (the Windows timing and X11 runs on AC power, the Windows and Linux `-race`
lanes, two reproducible bundle builds and a quiet hot-path run), the C5.2 night, which re-measures
every benchmark in full against the baseline `cf31e01` in package chunks that may span more than one
night (decisions D62(b), D65(b)), the C1.16 rig re-measure on that night, whose figure the
documentation then restates (D62(c), D65(a)), hosted CI on it, with the hosted release-version
bundles compared byte for byte with its frozen ones, a short live re-check, and the pre-registered
live evaluation. The figures in the table below are candidate 6's and candidate 7's
and stand until candidate 8's are recorded; the release is not published before they are. What has
been verified differs by target.

| Where | What the evidence shows |
| --- | --- |
| windows/amd64, the reference host | The only target installed into Claude Code: earlier release candidates' frozen bundles were installed into Claude Code 2.1.280 and run in real sessions by an agent on the owner's machine (decision D3, never human UAT). The hot-path budgets pass in a quiet run on AC power (B-A p99 30.7 ms and B-B p99 24.6 ms against 50; B-E p99 170.8 ms against 2,000; B-F p99 73.7 ms against 250 over 2,000 tool uses), and the ledger-resident hot-path test (X11) passed 3 of 3 rounds on AC. The whole tree passes under `-race`. |
| Hosted CI: ubuntu-latest (x86-64), macos-latest (arm64), windows-latest | The test suites, the end-to-end tests, the timing jobs and the hot-path budget gate run natively on all three. A hosted runner's disk is not the reference platform, so its fsync-bound timing rows are reported there, not gated (owner decision Q1), while the delivery ledger and every structural check gate. |
| Linux | Not installed into Claude Code. In a local Docker Desktop/WSL2 container the whole tree, the end-to-end tests and the product-child lane pass under `-race` as a non-root user. The fsync-bound rows, B-A and B-B, are **not verified in target** (D53(b)): the container's fsync is far slower than a native disk's, and hosted figures never become budgets. On such a disk the hooks switch to spool submode and nothing is lost. |
| macOS | Not installed into Claude Code. The test suites run on hosted macos-latest (arm64); darwin/amd64 is cross-compiled only. Whether a marketplace install keeps `bin/qompack` executable, and what Gatekeeper does with the unsigned binary, have not been observed. |
| linux/arm64, windows/arm64 | Cross-compiled and bundled; no test has run on either architecture and neither has been installed. |

The command and tool namespace comes from the plugin's own name, `qompack`, not from the
marketplace entry's name. Installed on windows/amd64 from a local marketplace whose entry is named
`qompack-windows-amd64`, a session listed the server `plugin:qompack:qompack`, the tools
`mcp__plugin_qompack_qompack__<tool>` and the commands `/qompack:<name>`; the entry's name appears
only in the plugin id, `qompack-windows-amd64@<marketplace>`, the install path and the session's
`plugins[].source`
([docs/install.md §9](https://github.com/AidanHT/qompack/blob/v0.3.0/docs/install.md#9-installing-from-the-public-marketplace)).
An install from the published marketplace has not been observed; if your session lists another
prefix, use the one it lists.

**Hooks as the host saw them.** Across the 20 real sessions of release candidate 7's live lane on
windows/amd64, Claude Code reported 474 hook calls and no hook failure or timeout (decision
D53(i)). These host-seen figures stay candidate 7's (decision D58(e)); candidate 8's live re-check
and the live evaluation are held to the same criterion. The arrival delta the host's stream shows
between a hook's start and its response, over the 417 measured pairs of the 19 sessions on that
candidate's bundle, is approximate (the stream carries no duration field):

| hook event | measured | p50 | p95 |
| --- | ---: | ---: | ---: |
| `PostToolUse` | 150 | 57 ms | 147 ms |
| `SessionStart` (compact) | 22 | 107.5 ms | 157 ms |
| `Stop` | 119 | 54 ms | 109 ms |
| `SubagentStop` | 22 | 58 ms | 91 ms |
| `UserPromptSubmit` | 104 | 51 ms | 100 ms |
| all events | 417 | 56 ms | 123 ms |

Of 455 pairs, 38 arrived before the stream's init event and were not measured: `SessionStart` at
startup, resume and fork (19) and `UserPromptSubmit` (19). `PreCompact` and `SessionEnd` have no
start and response pair on the stream.

**How the Windows timings were taken.** Every Windows reference timing was taken on AC power, with
the store under a path excluded from Windows Defender scanning (decisions D32, D53(h)). A run on
battery is not a reference measurement, neither a pass nor a fail, because on battery Windows
applies slower CPU, PCIe and NVMe power policies (D57(d)). On battery, or on any slow disk, the hot
path switches to spool submode as designed and nothing is lost (D53(c)).

## Late fixes

Release candidate 8's last two waves (decisions D67 to D72) changed the following, each listed in
full in the CHANGELOG.

- A healthy project no longer drops to passive recording when several windows start at once on a new
  project, when a window stays quiet past `runtime.daemon.idleExitSeconds`, or when a compaction you
  cancel (Esc) or that fails is followed by a prompt or an exit and then `--resume`.
- A `.qompack/run/state.bin` left saying the daemon is disabled or the mode is off, by a daemon that
  died without a clean stop, no longer stops the hooks: it counts only while that daemon still runs,
  and otherwise the configuration decides (D67(c)).
- A main-agent `Stop` cut short and replayed no longer shifts the turn number of every later record.
- A spooled copy of a `PreCompact` the daemon already sealed is no longer sealed a second time.
- A replayed `SessionStart` no longer re-anchors the scheduler or takes it from the live session it
  is bound to, and a daemon that never idles keeps scheduler bookkeeping for at most 256 sessions.
- A compaction no longer re-reads a large pasted prompt to open the next checkpoint.
- A forked session's checkpoint carries its parent's decisions as of the fork point, and a decision
  a sealed checkpoint truncated away is carried again (D67(a)).
- A drop reason that says to run `/qompack:pin --list` is no longer withheld as an outside path.
- A healthy store no longer logs a false "publication accounting incomplete" line when a file is
  removed or replaced while the background pass reads it.
- In a path-named tool argument, the rehydration block judges each piece, including pieces glued by
  a control character, a quote, a backtick, a non-ASCII space or another non-ASCII non-letter
  character (an ASCII `+ # ) ] } ! ^` is not; see Known limits below), each alternative of a
  `{a,b}` brace list, and names a shell builds at run time (`$(…)`, a cmd `%VAR%` after a run of
  dots, `~+`), so those spellings no longer show a refused or outside path; rarer ones remain,
  under Known issues below and in `docs/security.md` §1 (D71, D72).
- With a Read deny or ask rule in force, a rehydration build asks the host at most 64 times about
  checkpoint drops and 64 times about brace alternatives, and treats the rest as withheld, so a long
  session's rehydration no longer nears the 5 s compaction budget (D71(d)).
- ToolSearch's `select:` previews are shown in the block's pointers instead of being withheld
  (D67(l)), and section 6 explains a withheld pointer once, in a legend line under its heading.
- When one object comes from several refused paths, `recall`, `expand`, `why`, `re_read` and
  `dropped` give the same withheld reason on every read.
- Configuration violations are reported consistently: `status`, `doctor` and `self-test` agree, a
  command logs a violation once at `warn` with the `location=` that set it, only a daemon's start
  writes it to `LOUD.log`, and no command creates `.qompack/` just to record a configuration
  violation in a directory that has none.
- With `runtime.mode` `off`, `status` says the mode is off instead of reporting a decoding error, and
  `doctor` no longer says it asked a daemon to start.

## Known limits and accepted residuals

Each was accepted for 0.3.0 by the named decision and is documented in
[docs/cannot-do.md](https://github.com/AidanHT/qompack/blob/v0.3.0/docs/cannot-do.md), except the
Windows directory-sync limit, which is in
[docs/security.md](https://github.com/AidanHT/qompack/blob/v0.3.0/docs/security.md#8-known-limitations),
the backup refusal after a downgrade, which is in
[docs/backup.md](https://github.com/AidanHT/qompack/blob/v0.3.0/docs/backup.md) and
[troubleshooting §6](https://github.com/AidanHT/qompack/blob/v0.3.0/docs/troubleshooting.md#6-configuration-and-schema-compatibility),
the second daemon a missed connect can start, which is in
[troubleshooting §1](https://github.com/AidanHT/qompack/blob/v0.3.0/docs/troubleshooting.md#qompack-status),
and the replay evaluation's recorded-corpus tier, which the close-out ledger records (D67(g)).

- Each journal rotation, every 65,536 deliveries, pauses capture for 2.3 to 6.8 s, and store GC
  halts past 65,536 carried unacknowledged leases (D6, D16).
- A compaction at the edge of session-start's budget, or one that meets a daemon spawned late, can
  get the "rehydration deferred" note instead of the rehydration; the request is spooled and
  replayed, and `dropped()` then says the rehydration never reached the model (D29).
- A prompt captured out of host order is flagged, never renumbered (D35(b), D38).
- A `SessionEnd` that arrives while the daemon is stopping waits in the spool for the next session
  (D35(c)).
- Spool submode lasts until the session or the daemon ends (D44).
- A retrieval page beside interleaved redacted text can be shorter than the largest that fits; it
  still carries `next_span` (D48).
- Writing a novel object (PutBytes) and capturing a 256 KB tool result miss their budgets; the cost
  is after the hook's acknowledgement, so no hook waits on it (D54).
- A `PreCompact` that arrives while a client-spool replay is already running waits behind it; the
  seal goes ahead at its 500 ms bound and names what it left (D56(e)).
- `qompack fsck` run beside a live daemon can report an evidence-class retention root as not held
  while the daemon is still publishing it. Stop the daemon and run `fsck` again; a result taken with
  the daemon running is a snapshot (D57(b)).
- Windows directory sync relies on NTFS journaling, so a backup reported certified can revert after
  a power cut (D24, D26).
- Read rules that exist only in the running session (session-only rules, CLI flags, hook policies)
  are not seen (D7).
- On Linux and macOS, a connect to a running daemon that has stopped accepting, with its connection
  queue full, fails at once instead of waiting out its budget, so a hook, a command or
  `session-start` reads it as no daemon and a second daemon is started. That daemon finds the
  running one's lock and exits, and nothing is lost
  ([troubleshooting §1](https://github.com/AidanHT/qompack/blob/v0.3.0/docs/troubleshooting.md#qompack-status),
  D61(c)).
- After a daemon is killed mid-session, the daemon that takes the project over can reach its idle
  exit without writing `index/files.json`, so `qompack fsck` then exits 1 naming `index.files`
  absent. Nothing is lost: `qompack fsck --repair --yes` regenerates the view, and the next
  session's flush writes it (D59).
- When the original request is too long for the rehydration block, older evolution entries (your
  later prompts) are not re-admitted into the room the block leaves unused, because authority order
  comes first. Each is named in section 7, and `dropped()` lists them (D59).
- A compaction that dropped material is never silent: when the budget admits no section, the
  block is a loss notice naming the loss and how to restore it. Below the smallest loss notice,
  nothing is injected: a rehydration budget too small for even "N items dropped; call dropped()"
  gets no block, and the drop report and one `LOUD.log` line name the loss instead (D59(b),
  D60(c)(ii)).
- In its pointers, the rehydration block withholds a path your saved Read rules deny and an
  absolute path outside the project. File pointers and structured argument summaries are judged
  whole, and a path-named value holding several paths is judged piece by piece. A free-text summary
  (a command line, a query) is shown only when a whitelist proves it safe (decisions D63 and D64):
  every token is built from letters, marks, digits and a small set of safe punctuation, names no
  absolute or escaping path, and holds no rule's literal or withheld path's name where a name
  starts. The whitelist withholds more than it must, by design (D64(4)): a command with a variable,
  a glob, a regular expression, a `%` escape or a `name:` shape where a path may start
  (`localhost:3000`, `format:%h`) is withheld even when it names no denied file, and so is any text
  that mentions a rule's literal. The project root counts as one root unit only when its spelling
  is plain (letters, marks, digits, `-`, `_`, `.`, its separators and single spaces, no word
  starting with `-`); under any other root a summary that spells the root is withheld (D64(1)). The
  whitelist does not resolve aliases (8.3 names, links), cannot see names built at run time, and
  judges a summary as the store previews it, which collapses runs of whitespace (D60(c)(iv)).
  Globs in free text are always withheld; a structured glob (a lone Glob or recall pattern) that
  selects a refused file the block never recorded, without spelling its literal (`private/d*`), is
  judged as written (D60(c)(iv)). Inside one path-named value, a rooted path glued after one of
  `+ # ) ] } ! ^` (`a.txt+\Windows\win.ini`) is not judged as a path, so it can be shown; the same
  text in free text is withheld (ADR 0011 §23). The records in sections 2 to 4, your own prompts
  and the model's own earlier text, are not screened (D60(c)(i) for sections 3 and 4, D62(f) for
  section 2).
- On macOS, Qompack assumes the default case-insensitive volume: it compares paths and the Read
  rules' patterns without regard to letter case, so on a case-sensitive APFS volume two names that
  differ only in case are read as one (D67(m)).
- The replay evaluation's recorded-corpus tier is not exercised in 0.3.0: no recorded corpus is
  committed and no test reads real transcripts, so the replay evidence is the replay gate's
  (D67(g)).
- A quiet live session is counted as ended until its next hook: with no hook for
  `runtime.daemon.idleExitSeconds` (a long reply with no tool call, a long compaction), the daemon
  logs it as abandoned; its next hook revives it, and nothing captured is lost (D62).
- When a command's connect to a running daemon misses its budget, the command can start a second
  daemon, which finds the running one's lock and exits; nothing is lost (D61(c)).
- In a project with two live sessions, another session's tool use counts toward the scheduler's
  bound session and can close that session's segment (D67(b)).
- `qompack backup create`, `backup verify` and `backup restore` refuse while a newer
  `settingsVersion` is in force, as after a plugin downgrade; take the backup with the newer build
  first (D59).
- Not in this build: a manual checkpoint command, `qompack bench`, an operator command that stops
  the daemon, and any automatic downgrade of the store format.

The full per-capability status is the table in
[docs/release.md](https://github.com/AidanHT/qompack/blob/v0.3.0/docs/release.md#capability-status-at-030).

## Known issues

Minor defects this release does not fix, each recorded in the close-out ledger (decisions D66(d)
and D67(o)).

- Claude Code windows left open with no hook past `runtime.daemon.idleExitSeconds` (30 minutes by
  default) through two daemon idle exits, with a new window started after each, make the second
  start fail `session_start.fires`, and the project drops to passive recording. It cannot happen
  once any session of the project has ended or compacted; to recover, exit one session normally,
  and full recording returns after two later session starts pass their checks
  ([troubleshooting §1](https://github.com/AidanHT/qompack/blob/v0.3.0/docs/troubleshooting.md#qompack-status)).
- When the rehydration budget runs short and scores tie, a forked session's block can keep a
  decision inherited from its parent ahead of the fork's own. The cut decision is still named in
  `dropped()`, and `why()` retrieves it.
- In a project with a Read deny or ask rule, a rehydration build asks the host about at most 64
  path-keyed checkpoint drops, those a summary or a drop reason names first. Later ones show as
  "(path withheld)" in section 7 and in `dropped()`, and a section 6 summary that names one may be
  withheld too: more is hidden than must be, never a refused path (D71(d)).
- A rehydration build with no checkpoint drops costs about 1.7 times candidate 7's, about 2 ms more,
  because of the summary whitelist (D63). That is far inside the 5 s compaction budget.
- A hook's "invalid configuration value" line in the day log does not say which file, variable or
  flag set the value, and `qompack config print --provenance` shows that key only as
  `fallback after violation`. To find it, run `qompack status`: its `warn` line in the day log names
  the source under `location=`, as the daemon's start line does
  ([troubleshooting §6](https://github.com/AidanHT/qompack/blob/v0.3.0/docs/troubleshooting.md#6-configuration-and-schema-compatibility)).
- With `runtime.mode` `off` in `config.json`, a hook whose own read of its delivery fails still
  appends one line naming the read error to `.qompack/logs/hook-quiet-YYYYMMDD.jsonl` where
  `.qompack/logs/` exists, until `.qompack/run/state.bin` also says off. To have the hook path write
  nothing at all, remove the plugin
  ([troubleshooting §8](https://github.com/AidanHT/qompack/blob/v0.3.0/docs/troubleshooting.md#8-safe-disable),
  Steps 3 and 5).
- After a daemon restart, the first compaction of a session whose newest prompt is a very large paste
  reads that prompt once in full.
- If a `PreCompact`'s reply misses the hook's 15 s deadline and the hook's spooled copy is replayed
  before the slow seal finishes, that compaction gets two checkpoints. The copy is never dropped
  before a seal succeeds, so the compaction always keeps one.
- A `SessionStart` replayed from a hook's spool, for a session that had ended or that this daemon
  never saw, marks that session live: a later replayed delivery of it can bind an unbound scheduler
  to it until the live session's next start, and the daemon's idle exit waits for that session's
  silence timeout.
- A segment close owed by a delivery whose first run was cut is held only in memory. If that run, its
  replay at `Stop` and its replay after a restart are all cut, the close is never made and the span
  stays in the next segment, at a coarser boundary; nothing captured is lost (D67(b)).
- Five more are listed under Known limits above: the single scheduler account per project, which
  lets another session's tool use close the bound session's segment (D67(b)); the second daemon a
  missed connect to a busy daemon can start, which loses the lock and exits (D61(c)); the
  recorded-corpus tier of the replay evaluation, not exercised (D67(g)); macOS's assumed
  case-insensitive volume (D67(m)); and a rooted path glued after one of `+ # ) ] } ! ^` inside one
  path-named value, which can be shown (ADR 0011 §23).
- The rehydration block judges each path in a path-named tool argument, but a few rare spellings can
  still show a path outside the project or one a Read rule refuses: a cut-off `~[name`; a home
  directory named by a login that holds `@`, `$` or a non-ASCII letter; a Windows `%VAR%` whose name
  is not an identifier; look-alike Unicode slashes or dots (`／`, `∖`, `．`); and a non-canonical
  spelling (`a/./b`) of a refused path whose file name is shorter than 3 bytes (D72(a)). They are
  the first fix planned after this release.
- The description of `/qompack:status`, and `docs/commands.md` generated from it, say status reports
  the last decision, but neither the status page nor `qompack status --json` carries one. To see a
  recorded decision, run `/qompack:why <decision-id>` (D76(b)).
- After a crash that left an object written but not indexed, the next session end's garbage
  collection deletes that object, the one the daemon's startup accounting reported, before an
  operator can audit it. No capture content is lost: the capture keeps its bytes inline in its
  sidecar, and `qompack fsck` still names the gap. To keep the object itself, copy the store before
  the next session ends
  (D76(c); see [backup](https://github.com/AidanHT/qompack/blob/v0.3.0/docs/backup.md)).
