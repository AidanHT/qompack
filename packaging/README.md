# Packaging contract

What `go run ./tools/devtool bundle` produces, what its identity documents mean, and what has and
has not been validated about the result. This is the contract every later SP-17 task builds on: the
platform matrix, `fsck`/`doctor`, the release workflow and the install/upgrade end-to-end flow all
consume the bundle described here.

## 1. Layout

One directory per release target, assembled under `dist/bundle/` (git-ignored — a bundle is a build
output, never a committed artifact):

```
qompack-plugin-<version>-<os>-<arch>/
├── .claude-plugin/plugin.json     generated by internal/pluginmanifest
├── .mcp.json                      generated by internal/pluginmanifest
├── hooks/hooks.json               generated by internal/pluginmanifest
├── commands/*.md                  generated by internal/pluginmanifest (seven)
├── bin/qompack                    built for this target (bin/qompack.exe on windows)
├── BUNDLE.json                    identity: what this bundle is and what is in it
└── checksums.txt                  sha256sum-format listing of everything above
```

The bundle root **is** the plugin root: a host looks for `.claude-plugin/plugin.json` beside it, not
one directory down, so the `plugin/` prefix `internal/pluginmanifest` uses for this repository's own
checkout is stripped during assembly.

It is a directory, not an archive. An archive would interpose a compression format, a member order
and a modification time between the bytes this repository produces and the bytes a host reads, and
each of those is a place where two builds of the same source stop agreeing.

**There is no shell launcher.** The manifest is identical on all six targets: every hook and the MCP
server invoke `${CLAUDE_PLUGIN_ROOT}/bin/qompack <subcommand>`, which the host expands to the
installed plugin directory. One manifest for every OS is what keeps the generated tree a single
source; see the open question in §7 about how that string resolves on Windows.

## 2. Identity — `BUNDLE.json`

```json
{
  "name": "qompack",
  "version": "v0.2.0-602-gacbb0f2",
  "target": { "os": "windows", "arch": "amd64" },
  "go": "go1.26.6",
  "source": { "commit": "<full 40-character sha>", "dirty": false },
  "files": [ { "path": "bin/qompack.exe", "sha256": "…", "bytes": 7943680 } ]
}
```

| field | meaning |
| --- | --- |
| `name` | the plugin's own name; always `qompack` |
| `version` | the one version string (§3), identical to `plugin.json`'s and to the binary's |
| `target` | the GOOS/GOARCH the binary in `bin/` was built for |
| `go` | the toolchain that compiled it, e.g. `go1.26.6` |
| `source.commit` | full SHA of `HEAD` at assembly time; empty when git was unavailable |
| `source.dirty` | true when the worktree carried uncommitted changes |
| `files` | every file in the bundle except `BUNDLE.json` and `checksums.txt`, sorted by path |

`files[].path` is slash-separated and sorted, so a Windows assembly and a Linux one produce the same
document. `source.dirty` is not cosmetic: a bundle assembled from a dirty tree cannot be reproduced
from its commit, so it is not a release artifact, and nothing but this flag would say so afterwards.

**There is no timestamp anywhere in a bundle.** A clock reading would make every bundle unique and
the determinism rule (§4) unenforceable.

`checksums.txt` lists the same files in the same order in `sha256sum` format — digest, two spaces,
path, LF — so it is verifiable with `sha256sum -c checksums.txt` from inside the bundle directory by
somebody who has none of this repository's tooling. The two identity documents describe the bundle,
so they cannot describe themselves and neither is listed in either one.

## 3. Version — one source, three destinations

```
--version <v>            if given
else `git describe --tags --dirty`   if it yields anything
else internal/core.Version           the compiled-in default
```

The resulting string is stamped into all three places in the same run:

- the binary, via `-ldflags "-X github.com/qompack/qompack/internal/core.Version=<v>"`;
- `plugin.json`, via `pluginmanifest.Default(<v>)`;
- `BUNDLE.json`'s `version`.

So `qompack version`, the manifest the host reads and the identity document cannot report three
different versions of the same bundle.

`git describe --tags` is used **without** `--always`: on a repository with no tags it fails rather
than falling back to a short SHA, because a commit hash is not a version and stamping one would make
the binary contradict the manifest.

## 4. Determinism

Two consecutive assemblies of the same source at the same version produce byte-identical
`BUNDLE.json` and `checksums.txt`. Three things buy that:

- `-trimpath` — no absolute source paths in the binary;
- `-buildvcs=false` — no VCS stamp in the binary. The commit is recorded in `BUNDLE.json` instead,
  where it is data rather than an input to the hash of every file beside it, and where an unrelated
  edit elsewhere in the worktree cannot move it;
- `-ldflags "… -buildid=…"` — the linker otherwise embeds a build ID derived from the action graph,
  which differs between two builds of the same source made in different working directories.

`build`, `build-all` and `bundle` all go through one helper (`goBuildRelease` in
`tools/devtool/build.go`) so the flag list cannot differ between them.

The rule is enforced by `TestAssembleBundle_Deterministic` (identity documents, over a fixture
binary) and `TestGoBuildArgs` (the flag list itself, which no test could read while it lived inside
the build call); real-binary reproducibility across two runs is evidenced in
`plans/sdd/V6-SP-17-packaging-hardening-and-release/commit1-evidence.md` §2. The test assembles
twice into two separate temporary directories rather than inspecting `dist/`, where a file left
behind by an earlier run would make a non-reproducible assembly look reproducible.

**One caveat on `--out`.** The rule holds for the bundle's own contents. `source.dirty` is read from
`git status --porcelain`, so an `--out` directory inside the repository but outside `.gitignore`'s
coverage makes the second run observe the first run's output as an untracked change and flip
`source.dirty` from false to true. The default `dist/bundle` is git-ignored and does not have this
problem; an `--out` elsewhere in the tree does.

**The goreleaser gap.** `.goreleaser.yaml` (its `builds:` block) still compiles with `-trimpath` and
`-s -w -X …Version=…` only — no `-buildvcs=false`, no `-buildid=`. Its binaries will therefore not be
byte-identical to `devtool bundle`'s until the release workflow task amends it. That file belongs to
the release task and is deliberately untouched here.

## 5. What is validated, and what is not

| check | what it actually says |
| --- | --- |
| `go run ./tools/devtool plugin-validate` | this repository's committed `plugin/` tree matches what `internal/pluginmanifest` generates. Repository self-consistency. |
| `claude plugin validate <bundle> --strict --json` | the **host's** own verdict on the bundle's manifest, run where the bundle sits. |
| `go run ./tools/devtool bundle --host-validate` | assembles, then runs the above against the host target's bundle and records the verdict, the CLI version and the bundle identity as evidence. |

Neither is an installed-plugin canary, and the evidence record says so in as many words. The
directory is validated **where it sits**, so installed manifest resolution, `${CLAUDE_PLUGIN_ROOT}`
expansion and launcher discovery remain unverified until the platform matrix covers them. Repository
JSON parsing alone never validates an installed plugin (Qompack.md §7.5); the in-repo validator is
complementary to the host's, not a substitute for it.

A record is written whether or not the CLI is present, and it always says which signal decided the
answer. `outcome` is one of `accepted`, `rejected`, `timed-out`, `could-not-run` or `unverified`,
and only `rejected` means the host judged the bundle wrong; `verdictSource` says whether the verdict
came from the CLI's `--json` `success` field or from its exit status alone (a future CLI that
renames the field must read as "no verdict", not as a failure). A pass requires a zero exit **and**
`success: true` — a non-zero exit is never overridden by the payload. `stdout` and `stderr` are
captured separately, so a warning line cannot make a good `--json` verdict unparseable. When the CLI
is absent the record carries `unverified: claude CLI not on PATH` — never a pass.

## 6. Targets and their evidence status

The six targets are 00-ARCHITECTURE.md §2.6's, shared with `build-all` and `bindeps`. A `--target`
outside this set is refused rather than built: a bundle for a seventh would carry an identity
document asserting a target nobody tested.

| target | status today |
| --- | --- |
| windows/amd64 | **built and host-validated** on this host — see `plans/sdd/V6-SP-17-packaging-hardening-and-release/commit1-host-validation.json` |
| windows/arm64 | built, unverified until the platform matrix (Task 2) or CI covers it |
| linux/amd64 | built, unverified until the platform matrix (Task 2) or CI covers it |
| linux/arm64 | built, unverified until the platform matrix (Task 2) or CI covers it |
| darwin/amd64 | built, unverified until the platform matrix (Task 2) or CI covers it |
| darwin/arm64 | built, unverified until the platform matrix (Task 2) or CI covers it |

"Built" means the cross-compile succeeded and the bundle assembled. It does not mean the binary was
executed, that a host loaded the manifest, or that the launcher was discovered on that platform.

## 7. Open questions for the platform matrix (Task 2)

These are deliberately unanswered here. Guessing at them is exactly what a matrix exists to stop.

1. **Windows resolution of `bin/qompack`.** The manifest names `${CLAUDE_PLUGIN_ROOT}/bin/qompack`
   on every target, while the Windows bundle ships `bin/qompack.exe`. Whether a Windows host appends
   the extension when it executes the hook command — and whether that differs between the hook
   runner and the MCP server launcher — is unverified. The alternatives if it does not (an
   extensionless copy, a per-OS manifest, a launcher shim) each cost something, and the choice
   should follow the measurement rather than precede it.
2. **Paths with spaces.** Plugin roots under `C:\Program Files\…` or `~/Library/Application
   Support/…` are ordinary; whether the host quotes the expanded command string is unverified.
3. **Non-ASCII paths.** A plugin root containing non-ASCII characters, and the console code page a
   Windows host runs hooks under.
4. **Long paths.** Windows `MAX_PATH` against a deep plugin root plus `commands/checkpoint.md`;
   `internal/paths` already carries the `\\?\` handling the product side needs, and whether the host
   applies the same is unverified.

## 8. Commands

```sh
go run ./tools/devtool bundle                          # all six targets into dist/bundle/
go run ./tools/devtool bundle --target windows/amd64   # one target
go run ./tools/devtool bundle --version v1.2.3         # override the version rule
go run ./tools/devtool bundle --out /tmp/b             # assemble somewhere else
go run ./tools/devtool bundle --host-validate --evidence <path>   # assemble, then ask the host
```
