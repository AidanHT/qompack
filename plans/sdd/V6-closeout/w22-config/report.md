## Assigned audit findings

- **minor** `internal/cli/doctor.go:729-737 (configViolationsRow: live := config.ViolationsFromWarnings(s.warnings))`: config.Warning.VersionedReset has a consumer it is missing. Doctor's config.violations row builds its live list with ViolationsFromWarnings, which drops a newer-settingsVersion reset. The row only counts a reset once a hook or command has written state/config-violations.json. So within one doctor run, config.violations says the configuration is clean while config.capture says one setting fell back. Wave 20 made a reset count as a 'setting' in this row, but only through the persisted record.
- **minor** `internal/cli/config.go:83-89 (reg.Counter("config.violations") counts leaf violations only); docs/troubleshooting.md:705-712 (§6 'After a downgrade')`: status disagrees with doctor and self-test in two ways. (1) status's daemon counter config.violations ignores a newer-settingsVersion reset, which the record, doctor and self-test all count as a setting. (2) The counter is cumulative from daemon start and the loud ring keeps the start line, so after following §6's procedure, self-test and doctor read ok while status still reports config.violations 1 and the stale loud line until that daemon exits. §6 says only that doctor 'reads ok as well'.
- **minor** `internal/cli/config.go:98-101 with :266-268 (syncViolationsRecord MkdirAll(l.State)); docs/troubleshooting.md:19-21; docs/user-guide.md:548`: This is a regression from candidate 7 introduced by recordedViolations. A command load now records a user-global, QOMPACK_* or --set newer-settingsVersion reset, and syncViolationsRecord runs MkdirAll on state/. So `qompack config print`, a read command the docs say does not create the layout, creates <dir>/.qompack/state/config-violations.json and .qompack/tmp in any never-used directory. That happens exactly in the downgrade case: a ~/.qompack/config.json written by a newer build. Candidate 7 did this only for a leaf violation, which is the carried open issue. Candidate 8 widens it to the reset.
- **minor** `internal/cli/config.go:41-46 (loadDaemonConfig comment) and :83-85 (LoadConfigAndReport Louds every leaf violation for every caller)`: The code comment states D59's rule as 'the daemon reports such a condition loudly once per start or change while hooks and commands log it at warn'. Commands still Loud every §11.3 leaf violation each time they run: `qompack mcp` at every session start and each /qompack: command. Each Loud is a line in the never-rotated LOUD.log for an unchanged, persistent condition. This is the class of F-C7-C49-2, at session or command frequency rather than per hook. The §6 table documents it, so the behaviour is disclosed but inconsistent with the rule the code itself cites.
- **minor** `internal/cli/capture_admission.go:120 (reportCaptureConfig runs before the runtime.mode=="off" return); docs/troubleshooting.md:1292-1295 (§8 Step 3)`: §8 Step 3 says that with runtime.mode=off 'What keeps being written. Nothing from the hook path.' When the same configuration also holds a §11.3 violation, every hook writes state/, tmp/ and state/config-violations.json, plus one warn line per hook in the day log. A mode-off hook with a clean file also removes an existing record. This predates candidate 8 (candidate 7 also did a WriteAtomic and a Loud per hook), but the off rung of the safe-disable ladder is documented as writing nothing.
- **minor** `tools/devtool/genconfigdocs.go:326 -> docs/config-reference.md:206-208 (Gated switches)`: This is carried and still unfixed. The generated reference says a refused gated switch 'is reported as a warning'. The code records it as a §11.3 invalid value: it goes to state/config-violations.json, is Loud once per daemon start, and is a warn per hook. troubleshooting §6 correctly says 'recorded as an invalid value'. The two docs contradict each other.
- **minor** `internal/cli/doctor.go:769-779 (doctorPersistedViolations: paths.ReadFileShared, unbounded, follows links)`: This is carried and predates candidate 8. Wave 20 hardened the hook and command read of the same record (recordHolds: no-follow, non-blocking, regular file, size-bounded). doctor still reads it with a plain, unbounded open, so a FIFO at state/config-violations.json hangs doctor off Windows, and a link to a large file is read whole. The same path now has two readers with different safety rules.
- **minor** `internal/cli/doctor.go:769-770 (doctorPersistedViolations); internal/cli/config.go:242 (syncViolationsRecord)`: Two carried, pre-existing items from w20-config have no disposition. (1) doctor reads state/config-violations.json with an unbounded paths.ReadFileShared, so a FIFO there hangs doctor (hooks are safe since 07ff04ad). (2) A command load whose newer-settingsVersion reset comes from the user-global, env or --set layer, run in a directory with no .qompack, creates .qompack/state/config-violations.json there. That conjures a store directory where there is no project store.
- **minor** `internal/cli/doctor.go:770 (doctorPersistedViolations -> paths.ReadFileShared -> internal/paths/replace_other.go:16 openShared = os.Open)`: Wave 20 made the hook's read of state/config-violations.json non-blocking: recordHolds opens it with paths.OpenSharedLeaf (O_NOFOLLOW|O_NONBLOCK), checks it is a regular file and bounds the read, and capture_config_fifo_unix_test.go pins this. doctor still reads the same record with a plain blocking os.Open off Windows. - nit `internal/cli/config.go:71-89 (warn loop and violation Loud loop both log each clamp warning)`: On every daemon start and every command load, each §11.3 leaf violation is logged twice in the day log: once at warn as 'configuration warning' (the clamp warning is a keyed warning) and once at loud as 'invalid configuration value, using default'. - nit `docs/troubleshooting.md:675-678 (§6 refusal 'Action')`: The Action has the operator re-run self-test and then 'run a hook: a new file under .qompack/spool/, or the layout appearing, is the confirmation'. self-test itself creates the full layout and starts a daemon even while the hook loader refuses, so after the self-test step the layout appearing proves nothing.
